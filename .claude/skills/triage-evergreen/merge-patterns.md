# What makes a good vs. bad evergreen PR

Generated by analyzing past evergreen PRs and whether the owner merged them. Read this before deciding whether to open a PR, and use it to sanity-check your plan.

The single strongest predictor is whether the fix addressed the true root cause at the right architectural layer:

| Addressed root cause? | Merge rate  |
|-----------------------|-------------|
| Yes                   | 94% (16/17) |
| Partial               | 25% (2/8)   |
| No                    | 0% (0/2)    |

Strikingly, almost every closed PR was well-scoped, well-documented, and well-tested. They failed on judgment, not craftsmanship.

## Merge rate by change type

- **Security dependency bumps — 100%** (#248, #264, #290, #358): minimal diff, lockstep lockfile, cited advisory, no call-site impact. #248 merged in 83 minutes.
- **App-layer security fixes — 100%** (#345 SSRF, #346 open-redirect): both did a self-review pass that caught a second vector before merge.
- **Observability/diagnostics — 100%** (#359, #361, #368, #370): read-only, behavior-preserving with backward-compatible fallbacks + tests. #368 self-merged in 10 minutes. Even partial fixes merged here — you can't break anything.
- **Logic fixes — 67%** (closed: #270, #371).
- **Error-handling / data-integrity / retry — 29%** (the danger zone). This is where changes touch status semantics, retry loops, or external causes the maintainer judges differently.

## The four ways closed PRs failed

1. **Fixing a non-existent / already-fixed problem from stale evidence** (#251, #270) — the highest-confidence kill signal. #270 ("Not a real bug. Read the logs better.") relied on PM2 restart counts that predated the real fix in already-merged #259.
2. **Changing user-facing field semantics without auditing downstream consumers** (#357, #360). The contrast: merged #369 solved the same problem but kept `status='completed'` and surfaced failures additively — same bug, opposite outcome, decided purely by layer of fix.
3. **Over-generalized logic introducing a new bug** (#362: mapping the whole 4xx range to one error code).
4. **Correct fix, wrong vehicle** (#284, #324, #371, #372) — maintainer wanted it deeper, simpler, smaller, or as a Discord alert rather than a code PR.

## Top recommendations to raise merge rate

1. **Re-verify the bug is live in current production before opening a PR** — correlate timestamps against recently-merged fixes and check for prior closed duplicates. (Prevents #251, #270.)
2. **Never change a user-facing field's semantics** (job status, error/event codes) without enumerating downstream consumers; surface failures additively like #369 did.
3. **Default to the smallest sufficient fix.** For >~150 LOC or cross-package changes, confirm the maintainer's preferred design first.
4. **Route non-code root causes** (billing, provider outages, infra) to a Discord alert, not a PR.
5. **Lean into the proven-safe categories** (security bumps, app-layer security, observability) — combined ~100% merge rate.
6. **Treat unrun tests as a red flag** — #357/#360/#371 all had vitest segfault, so claimed coverage was fictional and hid the consumer-breaking risk.

**Bottom line:** evergreen's rejected PRs are overwhelmingly competently built solutions to the wrong problem. The biggest available win isn't better code — it's better up-front judgment about whether the problem is real, live, and best solved with a PR at that layer.
